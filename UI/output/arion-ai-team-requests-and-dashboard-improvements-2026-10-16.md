# AI팀 요청사항과 2차 미팅에 따른 대시보드 개선안

작성일: 2026-10-16 · 협의용 초안

이 문서는 첨부 회의록과 현재 대시보드 v0.4 계약을 비교한 정리다. 회의록에 기록된 의견, 현재 구현, 새로 제안하는 개선을 구분한다. 아래 요청사항은 아직 AI팀에 전달하지 않았으며, 기능 변경이나 GitHub 커밋도 수행하지 않았다.

## 1. 먼저 합의할 방향

- **실시간 이상탐지**와 **비행 종료 후 소모 추세·비행 간 변화 분석**을 별개 기능으로 다룬다. 후자가 곧바로 검증된 SOH나 잔여수명을 뜻하지는 않는다.
- 회사 로그에 RPM·온도가 없으면 실제 제공 신호로 연구한다. 누락값을 0이나 추정 RPM으로 채우지 않고, 축소 입력 모델이 가능한지 AI팀이 판단한다.
- 기업의 ArduPilot 자료와 PX4 시뮬레이션 자료를 출처·프로필로 구분한다. MAVLink를 사용한다는 사실만으로 필드·단위·모드·센서 지원이 같다고 가정하지 않는다.
- 전처리한 **물리 단위 관측값은 실시간 전달과 NPZ 보관에 공통 사용**한다. 모델별 scaler·정규화·학습은 외부 AI 서비스가 담당한다.
- 입력 10Hz, 추론 주기, 결과 API 확인 주기, 화면 갱신 주기는 각각 합의한다. 대시보드 학습 실행 기능은 추가하지 않는다.

## 3. AI팀에 요청할 사항

우선순위 P0는 실제 연결 전에 필요한 합의, P1은 결과 해석·평가를 위한 인계 항목이다. 회의에서 새 기능으로 확정되지 않은 항목은 제안으로 표시했다.

| 우선순위 | 요청할 내용 | 받아야 할 산출물·답변 |
| --- | --- | --- |
| P0 | 전처리 담당 범위 | 공용 전처리기까지 AI팀이 제공하는지, 수집 담당자가 별도로 제공하는지와 담당자. 모델별 scaler는 AI 서비스가 적용한다는 경계 확인. |
| P0 | LSTM·Transformer의 과제 정의 | 각 모델의 대상(배터리/구동계 등), 정상·이상 정의, 예측 대상, 점수 의미·방향, 임계값 근거. 모델 간 점수는 직접 평균하지 않는다. |
| P0 | 실제 지원 신호와 축소 모델 | 회사 로그에서 사용할 특징·단위·순서, RPM·온도 제외 가능 여부, 필수/선택 신호, 모터별 판정 가능 여부. 명령값·관측값·시뮬레이션 생성값 구분. |
| P0 | 시간·윈도 규격 | 전처리 출력 주기, 창 길이(샘플 수와 초), stride, 추론 주기, 준비 시간, 마지막 불완전 창 처리, epoch·긴 공백에서 초기화 규칙. |
| P0 | 결측·오래된 관측 처리 | mask·status·age 사용법, TTL, 허용 결측률, 미지원 신호 처리, 반복 전달한 이전 값의 age 증가 규칙. 미래값을 이용한 보간 여부도 명시. |
| P0 | 서비스 실행 형태 | 우선 로컬 HTTP 서비스로 인계 가능한지, 실행 명령·의존성·모델 버전·결과 URL·예제 요청/응답·실패/준비 중 응답. 원격 서비스만 제공한다면 현재 어댑터 변경이 필요하다. |
| P0 | 모델 입력 취득 경로 | 대시보드의 공통 수락 구간을 조회할지, 동일 식별자가 있는 공용 스트림을 공유할지 결정. 현재 결과 API GET 요청은 원본 데이터나 X 배열을 자동 전송하지 않는다. |
| P0 | 전처리·NPZ 샘플 | 실제 생산 형식의 짧은 전처리 프레임과 같은 내용의 NPZ, 특징 명세·프로필·버전·해시. 정상 예제와 결측·중단·epoch 변경 예제. |
| P1 | 예측·잔차·근거 | 관측/예측/잔차의 단위, 잔차 부호·집계 방식, 관련 신호·입력 구간. 정규화 공간의 잔차와 물리 단위 잔차를 구분한다. |
| P1 | 경보 정책 | 임계값 초과 방향, 연속 초과·해제·히스테리시스·유효기간, 반복 결과의 event_id 정책. 임계값과 경보 정책은 AI팀이 결정한다. |
| P1 | 모델 인계 자료 | 모델·전처리·scaler 버전과 해시, 입력 특징·순서·주기·창·단위, 학습/검증 출처, 기체·환경 적용 범위. 가중치는 대시보드 측에서 서비스를 운영하는 경우 인계한다. |
| P1 | 평가 자료 | 비행 단위 train/validation/test 분리와 중복 창 누수 방지 설명, 정상 오경보·탐지 지연·이상 종류별 결과. 라벨이 없으면 정확도·재현율을 확정하지 말고 검증 한계를 기록. 시뮬레이션과 실측 평가는 분리. |
| P1·제안 | 비행 전체·이력 분석 | 한 비행의 소모 추세 결과와 이전 비행 대비 변화 결과를 제공할 계획이 있는지. 필요한 battery_id·vehicle_id·비행/충전 사이클·환경 메타데이터와 비교 조건. |

배터리·기체 ID, 펌웨어, 원본 메시지·단위와 운용 조건은 기업/수집 담당자의 확인도 필요하다. AI팀에만 확인 책임을 두지 않는다.

## 4. 데이터는 세 종류로 나눠 전달

| 데이터 | 전달 방식·현재 지원 | 포함할 내용 |
| --- | --- | --- |
| 실시간 전처리 관측 | HTTP JSON, `POST /api/sessions/{id}/frames` | `arion-processed-v1`, 세션·프로필·sequence·epoch·ns 시각·물리값·단위·mask·status·age·전처리 버전 |
| 보관·재생 데이터 | 60초 구간 NPZ, 종료 후 전체 NPZ | 화면과 같은 수락 프레임의 값·품질·시간축·식별자·metadata. 학습용 정규화 배열과 구분 |
| 모델 판정 | 제공자별 로컬 HTTP GET 결과 API | `arion-provider-results-v2`, LSTM/Transformer별 상태·버전·입력 참조·근거/판정 시각·점수·임계값·근거 |

### 4.1 프로필과 전처리 프레임

프로필에는 `feature_order`, 신호별 `unit/ttl_ms`, `sample_period_ms`, `preprocess_version`을 넣는다. 특징 수 F나 4S 배터리를 고정하지 않는다. 프로필이 달라지면 새 프로필 ID와 세션을 사용한다. UI/API에 남아 있는 `normalized`라는 입력 종류명은 모델 정규화를 요구한다는 뜻이 아니다.

아래는 **형식 설명용 시험 프레임**이다. 두 특징의 순서를 프로필에 등록했다고 가정하며, 값·주기·TTL·필수 특징은 실제 데이터와 AI팀 합의로 확정한다. `live-example`은 발급받은 세션 ID로 바꾼다.

```json
{
  "schema_version": "arion-processed-v1",
  "session_id": "live-example",
  "profile_id": "battery_minimal_10hz_v1",
  "sequence": 1,
  "epoch": 0,
  "source_time_ns": 1000000000000000123,
  "relative_time_ns": 0,
  "preprocess_version": "battery-physical-v1",
  "sample_period_ms": 100,
  "values": {
    "battery_voltage_v": {"value": 16.2, "unit": "V", "mask": true, "status": "valid", "age_ns": 0},
    "battery_current_a": {"value": 0, "unit": "A", "mask": true, "status": "valid", "age_ns": 0}
  }
}
```

- 실제 0은 위와 같이 `mask=true`다. 미관측은 `value=null, mask=false, status=missing, age_ns=null`로 구분한다.
- 10Hz로 과거 센서값을 다시 보내도 새 관측이 되지 않는다. `age_ns`를 증가시키고 만료 기준을 적용한다.
- `source_time_ns`는 현재 계약상 생산자 시계의 ns다. UTC로 추측하지 않으며 시계 종류·리셋 규칙을 인계한다. 공통 상대 시간·epoch는 서버가 수락 시 확정한다.
- 현재 모델의 `requirements.signals`로 선언한 신호가 근거 구간에서 결측·만료이면 정상/이상 판정이 거부된다. 선택 신호의 결측을 모델이 허용하려면 요구사항·검증 정책의 별도 합의/확장이 필요하다. RPM 없는 데이터를 필수 RPM 모델에 억지로 연결하지 않는다.
- 3D에는 실제 위치와 roll/pitch/yaw 또는 합의된 자세 데이터가 필요하다. 입력에 없으면 3D는 미지원 상태로 둔다. 각속도를 적분해 없는 yaw를 만들지 않는다.

### 4.2 저장·재생용 NPZ

| 키 | 형상·의미 |
| --- | --- |
| `X` | `[N,F]`, float64 물리값. 값 자체가 없으면 NaN |
| `mask`, `status`, `age_ns` | `[N,F]`, 유효성·상태·관측 나이. status 0 missing / 1 valid / 2 stale / 3 invalid, 미관측 age는 -1 |
| `tick_ns`, `source_time_ns` | `[N]`, 공통 상대 ns와 원본 ns |
| `sequence`, `producer_sequence`, `epoch` | `[N]`, 수락 순서·생산자 순서·공통 epoch |
| `row_id`, `row_sha256` | 행 식별자·공통 프레임 해시 |
| `rows` | 재생·출처 검증용 JSON 문자열 배열 |
| `metadata` | 특징 이름·단위·순서, 프로필·전처리 버전, 출처·세션·구간·해시를 담은 JSON 문자열 |

object/pickle은 사용하지 않는다. invalid/stale에 값이 남아 있을 수 있으므로 `X`만 읽어 유효값으로 간주하지 않는다. 모델별 정규화·윈도 생성은 AI 서비스에서 수행하고, 학습용 NPZ가 별도라면 변환 규칙과 원본 참조를 제공한다. 임의의 `X` 배열만 있는 NPZ가 현재 보관·재생 형식과 호환된다고 가정하지 않는다.

### 4.3 모델 결과

LSTM과 Transformer는 별도 제공자다. 현재 어댑터는 로컬 HTTP 주소만 연결하며 기본 500ms 간격으로 GET한다(제공자 설정값). GET 파라미터는 `run_id`, `provider_id`, `input_sha256`, `latest_sequence`다. **전처리 10Hz가 모델 추론 10Hz나 결과 GET 10Hz를 의미하지 않는다.**

AI 서비스가 공통 입력을 조회하려면 `GET /api/runs/{id}/input-segment?start_sequence=1&end_sequence=20`을 사용한다. 응답의 `processed_frames`와 `input_ref`를 함께 사용하면 화면·NPZ·분석 입력의 연결을 검증할 수 있다. 원본 프레임 해시를 임의로 계산해 서버의 수락 프레임 해시와 혼용하지 않는다.

아래는 **연결 계약 설명용 시험 응답**이다. 1~20번 입력이 0~1900ms에 해당한다고 가정했다. 64자리 a 해시와 세션·시각은 실제 `input-segment` 응답으로 교체해야 하며, 그대로 보내면 출처 검증에서 거부된다. 실제 모델 결과는 `origin=model`과 실제 버전·수치를 사용한다.

```json
{
  "schema_version": "arion-provider-results-v2",
  "provider_id": "lstm",
  "run_id": "live-example",
  "state": "ready",
  "results": [{
    "schema_version": "arion-analysis-v2",
    "event_id": "contract-example-001",
    "provider_id": "lstm",
    "run_id": "live-example",
    "model_version": "lstm-contract-example-v1",
    "kind": "detector",
    "origin": "fixture",
    "input_ref": {
      "kind": "stream",
      "session_id": "live-example",
      "start_sequence": 1,
      "end_sequence": 20,
      "segment_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
      "preprocess_version": "battery-physical-v1"
    },
    "epoch": 0,
    "start_ms": 0,
    "end_ms": 1900,
    "decided_at_ms": 1900,
    "valid_until_ms": 2400,
    "status": "suspect",
    "target": "battery",
    "score": 0.72,
    "threshold": 0.65,
    "title": "시험용 배터리 이상 의심",
    "description": "연결 형식 설명용이며 실제 모델 결과가 아닙니다.",
    "evidence": [{"signal": "battery_current_a", "unit": "A", "observed": 0, "predicted": 2, "residual": -2, "note": "시험값. 잔차를 관측-예측으로 정의한 예시"}]
  }]
}
```

`start_ms ≤ end_ms ≤ decided_at_ms ≤ valid_until_ms`이고 동일 세션·epoch·입력 구간을 참조해야 한다. 실시간에서는 수신된 입력보다 미래의 판정 시각을 보내지 않는다. 종료된 비행의 유효기간은 비행 종료를 넘기지 않는다. 재생 시 판정 시각 이전에는 결과를 숨긴다.

준비 중은 `warming_up`, 판정 불가는 `unavailable`로 전달하고 정상으로 대체하지 않는다. 모델 점수는 확률이나 건강도 %로 바꾸지 않는다. 모델 비교를 위해서는 같은 비행·대상·epoch·근거 구간에 대한 응답을 요청한다. 창 길이가 다른 모델의 결과를 같은 입력 결과인 것처럼 강제로 맞추지 않는다.

현재 `evidence`는 항목별 스칼라 observed/predicted/residual을 담는다. 예측·잔차의 전체 시계열이 필요하면 시간축·단위가 있는 별도 계약을 확장해야 한다. 아래 개선안의 `analysis_scope`, 비행 요약, 비교 조건 등도 **현재 API 필드가 아닌 협의 제안**이며 기존 응답에 임의로 추가하면 안 된다.

비행 전체/이력 분석을 추가하려면 `analysis_scope=window|flight|history`, 기준 비행 ID, 비교 조건 등의 **새 결과 규격**을 검토한다. 현재 `detector/explanation` 응답에 열화 지표나 SOH를 억지로 넣지 않는다. 검증된 정답·측정 근거 없이 SOH %, 잔여수명, 자동 정비 권고를 추가하지 않는다.

권장 진행 순서는 **가용 데이터·전처리 담당 확인 → 프로필/최소 입력·서비스 계약 합의 → 동일 프레임/NPZ/모델 입력 대조 → 두 실제 서비스 연결 → 비행 종료 요약 → 조건을 맞춘 비행 간 비교**다. 이번 정리에서는 코드를 변경하지 않는다.

## 6. AI팀에 전달할 짧은 요청문

> 대시보드는 공용 전처리 결과를 실시간 표시하고 같은 프레임을 NPZ로 저장하며, LSTM·Transformer 결과를 독립적으로 비교하는 구조입니다. 학습과 모델별 scaler 적용은 AI 서비스에서 수행합니다.
>
> 연결 준비를 위해 ① 전처리 담당 범위, ② 실제 사용 특징·순서·물리 단위와 RPM/온도 없는 축소 입력 지원 여부, ③ 출력 주기·창 길이·stride·추론 주기·결측 처리·준비 시간, ④ 모델별 점수·임계값·경보 정책·예측/잔차 정의, ⑤ 로컬 HTTP 실행 방법과 모델 버전·예제 응답, ⑥ 동일 구간의 전처리 프레임/NPZ 샘플, ⑦ 학습·검증 분리와 적용 범위를 요청드립니다.
>
> 현재 대시보드의 결과 API 조회는 입력 배열을 자동 전송하지 않으므로, 공통 수락 프레임 조회 방식과 입력 구간 참조도 함께 맞추면 좋겠습니다. 회의에서 제안된 비행 전체 소모 추세·이전 비행 대비 변화는 실시간 이상탐지와 별도 결과로 제공 가능한지 확인 부탁드립니다. 실제 SOH나 잔여수명은 검증된 결과가 있을 때만 표시하겠습니다.
