# M19–M21: 실시간 수신 정지와 RPM 경로 수정

2026-11-15. RC13 가시 시연의 실패를 출발점으로 삼았다. 기존 배포와 모델,
비행 원본, 실패 증거는 유지한다. 이번 범위는 로컬 수신·기록·표시 및
PX4 실행기의 종료 처리다. 실기체 정확도나 전압 예측 성능 개선은 아니다.

## 원인과 변경

- RC13은 메시지마다 보통 두 번 `fsync`하고, UDP가 계속 들어오면 수신 루프가
  실행권을 넘기지 않았다. 30 ms 저장 지연과 UDP 60개로 API 4.147초 정지를
  재현했다. 별도 기록 스레드에서 최대 100 ms/1 MiB 단위로 묶어 저장하고,
  매 수신 묶음마다 HTTP·WebSocket 작업에 실행권을 넘긴다. 원본·순서·수신 시각은
  유지하며 종료/연결 해제는 마지막 fsync까지 기다린다. 급작스러운 전원 차단은
  아직 동기화하지 못한 묶음을 잃을 수 있다. 대기 버퍼는 16 MiB 제한이며,
  초과/저장 실패는 조용히 버리지 않고 수집 오류로 표시한다.
- 첫 수정본의 가시 비행은 180초 랜덤 기동·착륙·시동 해제·자식 종료를 완료했다.
  기록 227.3초 중 214.7초(94.5%)가 사용됐다. 첫 173회 API 관측에 실패가 없었고
  최대 health 응답은 28.5 ms였다. 그러나 약 50초마다 0.17–0.22초씩 수신이
  밀린 뒤 패킷을 몰아서 읽었다. 원본 재생 부하에서 generation 2 GC의
  70–134 ms 정지를 재현했다. 두 번째 수정은 소켓/시리얼 수신과 시각 기록을
  가벼운 별도 프로세스로 분리한다. API가 450 ms 정지해도 수신 시각이 몰리지
  않는지 시험한다. 전달 큐는 256패킷으로 제한하며 종료 시 받은 패킷을 비운다.
  별도 프로세스는 이미 열린 전용 descriptor만 물려받고 비행 명령을 만들지 않는다.
- 초기 HEARTBEAT가 10초 내 오지 않으면 자동 설정이 끝나던 문제를 고쳤다.
  선택한 연결이 살아 있는 동안 해당 system/component를 기다리며, 출처가
  확인된 뒤에만 메시지 주기를 요청한다. ACK 타임아웃의 모호한 재시도는 하지 않는다.
- ESC_STATUS(291) 주기 요청을 선택 항목으로 추가했다. 설치된 pymavlink에는
  정의가 없어 PX4에 고정된 공식 XML로 해당 메시지 클래스만 생성했다.
  기존 파서의 framing·CRC 검증을 유지한다. C 인코더 패킷과 손상 CRC를 시험한다.
  RPM/V/A를 그대로 사용하고 signed RPM과 실제 0을 보존한다.
- 현재 시뮬레이터는 정답 파일에 `omega_rad_s`를 쓰지만, capture 모드에서
  모터 명령을 ESC RPM으로 되돌려 주는 경로는 꺼져 있고 실제 ESC 피드백도
  발행하지 않는다. 이전 수신 기록에 ESC/UNKNOWN 메시지는 없었다.
  이 구성에서 RPM은 **미수신**이 맞으며, PWM이나 평가 정답을 관측값으로
  대입하지 않는다. ESC 피드백 센서 경로 추가는 별도 확장으로 남긴다.
- PX4를 `-d`/DEVNULL로 실행해 부모 stdin 종료 후 콘솔 반복을 차단한다.
  SIGTERM을 예외로 전환해 기존 소유 자식 정리 절차가 실행되게 한다.
  이전 exit 143 신호의 발신자는 당시 기록만으로 특정하지 못했다.

메시지 기준: [공식 ESC_STATUS](https://mavlink.io/en/messages/common.html#ESC_STATUS).
생성 기준은 PX4 MAVLink submodule `5bfd76d80281f6027134e854aafe6cb3dbfbe9e1`의
common.xml이다. 현재 메시지 정의와 설치된 라이브러리가 같다고 가정하지 않았다.

## 검증 상태

- 백엔드 전체 최초: 108 통과·새 시험 2 실패. 한 건은 시험이 저널 헤더를
  데이터 행으로 읽은 오류, 한 건은 ESC 정의 누락을 발견한 실패였다.
  수정 후 영향 범위 59개 통과. 중복을 빼면 전체 110개 통과 범위다.
- UI 26개 통과 및 TypeScript/Vite 빌드 성공.
- 시뮬레이션 263개 통과. 실제 프로세스에 SIGTERM을 보내 자식 회수를 확인했다.
  두 번의 초기 검사 환경 오류(pytest/jsonschema 없음)는 별도 기록했고,
  기존 Python 3.12 환경들의 설치된 의존성으로 실행했다. 새 패키지는 설치하지 않았다.
- 시뮬레이션 실행기와 새 시험만 생산자 검토 목록에 반영하고 기존 설치기의
  seal을 실행했다. 이전 source/runtime/source_lock은 해시별/작업 증거에 보존했다.
  물리·PX4 바이너리·프로파일·입출력 계약은 그대로다.
- 수신 프로세스 분리 후 백엔드 전체 **111개 통과**. 최종 후보 Python 3.10에서
  수신/저장/ESC 회귀 **5개**, doctor **CPU 16종** 통과.
  종료 후 재생 수정은 영향 범위 35개와 수정된 신규 시험 1개, 최종 저널 시험
  6개를 통과했다. 전체 112개를 한 번에 재실행한 결과로 표현하지 않는다.
  배포 도구 시험 8개도 통과했다.
- 최종 가시 시연은 180초 랜덤 기동 후 착륙·시동 해제·정상 종료했다.
  기록 226.311초 중 213.5초(94.339%)가 **9.6–223.1초 단일 연속 구간**이다.
  초기 이력 수집 후 비행 중 이력 재초기화가 없었다. 초기 9.6초와 착륙 뒤
  목표 상승률 입력 미제공 3.211초를 제외했다. 실제 건강 판정은 보정값 없음으로
  unavailable이며 정상으로 가정하지 않았다.
- 최종 원본에서는 150 ms 초과 전체 수신 공백이 없었다. PX4/Gazebo exit 0,
  자체 소켓 회수 완료. 1초 간격 로컬 API 관측의 상세 수치는 verification.json에 있다.
  종료 후 재생에서 2초 관측 제한 초과 1회가 있었고, 아래 추가 수정으로 처리했다.
  이 측정은 최대 지연의 절대 보장이나 실기체 장시간 검증이 아니다.

상세 증거: `ai/reports/live-repair-20261115/`.
네 개발 지침은 기존 `ai/reports/code-review-20261115/guidelines/`의 조회본을
읽고 적용했다. 원인 재현, 변경 범위 제한, 마일스톤별 검사, 실패 기록 보존을 따른다.
자동 생성된 ESC 메시지 클래스는 공식 wire 필드명·생성 구조를 유지한다.
백엔드·배포 코드의 Ruff 검사와 서식 검사는 통과했다. 봉인된 시뮬레이션
실행기의 기존 전체 서식은 이번 종료 처리와 무관하므로 일괄 변경하지 않았다.

## 검증 대기

실물 ESC/FC의 RPM 제공 여부·무선/USB 장시간 수신, 실제 PX4 ULog,
정상/이상 근거가 있는 독립 로그의 보정·적응·검출 정확도는 별도다.
기존 BIN 3개는 건강 상태 unknown을 유지하며, 전압 예측 오차는 미해결이다.


## 종료 후 재생 전환 추가 수정

최종 비행 수신은 연속이었지만 종료 후 큰 저널을 재생하는 순간 API 관측 한 번이
2초 제한을 넘었다. WebSocket 초기 연결/갱신에서 `store.get`이 디스크 기록을
웹 이벤트 루프에서 다시 파싱할 수 있었다. 이 두 경로를 작업 스레드로 옮겼다.
500 ms의 느린 재생 읽기 중 health 응답과 WebSocket 결과를 함께 검사한다.
첫 시험의 응답 래퍼 접근 오류는 수정하고 별도 재검사 기록으로 남겼다.
이 마지막 변경은 소켓 수신·저장·AI 모델을 바꾸지 않는다. 최종 배포에서는
실제 완료 기록을 다시 여는 동안에도 응답을 확인한다.
최종 포장 무결성·CPU 진단·패키지 회귀·화면 재열기 결과는 배포 옆
`.tar.gz.release.json`과 `ai/reports/live-repair-20261115/`에 기록한다.
