# M22–M24: 전체 로그 사용률과 X500 로컬 적응·보정·판정 시연

2026-11-15. 사용자가 실제 로그의 1% 사용률과 X500 시연의 판정 불가를
지적하고, 비행 기록 몇 개로 파인튜닝부터 판정까지 실행하도록 요청했다.
제품 코드를 고치거나 원본 모델/임계값을 덮어쓰지 않고 RC14의 기존 API와
보이는 UI/Gazebo로 실행했다. 원격 GPU는 사용하지 않았다.

## M22 — 실제 로그의 1% 원인

이전 시연은 00000011.BIN 전체 3,239.056초 중 첫 비행 33.7초만 선택했다.
전체 런 요약의 1.04%는 이 선택 비율이며 입력 유효율이 아니다. 첫 비행의
입력은 337/337프레임 유효했다. 나머지 99%가 손상됐다는 뜻이 아니다.

같은 앱에서 EV 이륙/착륙으로 확인한 5개 구간을 모두 준비하고 LSTM/Transformer
원본 모델로 재분석했다. 16,434프레임, 1,643.4초(27분23.4초)를 사용했다.
각 선택 구간 입력 유효율은 100%, 파일 전체 범위 대비 사용률은 50.737%다.
나머지 1,595.656초는 선택한 비행 범위 밖이다. 지상 시간/기록 공백을 비행
데이터로 보간하지 않았다. 건강 상태는 unknown이며 정상 학습/보정에 쓰지 않았다.

## M23 — X500 판정이 없었던 이유와 실행 계획

원본 X500 모델의 과거 평가 보정과 새 로컬 프로파일·MAVLink 수신 시간축의
보정은 서로 다른 결합이다. 기존 시연은 예측만 하고 새 결합에 맞는 보정 기준을
등록하지 않아 판정이 unavailable이었다. X500이라는 이름만으로 원본 threshold를
복사하지 않는다. 이번에는 보정과 활성화까지 수행한다.
구체적으로 원래 forecast는 `normal-postprocess-v7`, 종료 후 모델은 자체의
두 성분 scale/threshold를 사용한다. 현재 로컬 흐름의 1초 ahead 최대 표준화
잔차와 구간 전압 표준화 RMSE는 별도 점수다. 기체 이름뿐 아니라 점수 정의와
입력 시간축까지 다르므로 기존 숫자만 그대로 대입할 수 없다.

고정한 모델은 forecast_lstm_h64_l2와 run_health_lstm_h64_l2다. 정상 조건의
이전 완료 기록 1회로 출력층만 CPU에서 5 epoch 적응했다. 개발 비행 없이
사전에 고정한 마지막 epoch를 사용한다. 원본 encoder와 scaler는 유지한다.
이전의 다른 기록 1회에서 보존된 5개 구간 모두 변경 전후를 비교했다.
두 이전 기록은 seed 20261115를 반복한 경로라 일반화 검증으로 해석하지 않는다.

보정 2회는 seed 20261121/20261122, 마지막 평가 1회는 20261123으로 잠갔다.
기준은 미리 정한 99% 경험적 분위수다. 원본과 적응 모델 각각 별도 보정하며,
최종 평가 결과를 본 뒤 모델·epoch·구간·기준을 바꾸지 않는다.

이전 기록 전체 5개 구간의 비교에서는 forecast 전압 RMSE가 0.06012→0.05743 V,
종료 후 전압 기준 RMSE가 0.32270→0.31359 V였다. forecast의 yaw는 소폭
악화했다. 이는 같은 경로를 반복한 비교이며 최종 독립 평가 결과와 구분한다.

정상 근거는 잔차 크기가 아니라 시뮬레이터의 rpt_00 배터리, 정상 추진계,
confirmed_healthy 시나리오와 완료/운용 범위 검증이다. GUI preview의 기존
생산 학습 제외 표시는 유지한다. 이번 명시적으로 요청된 로컬 시연에만 사용하며
고정된 생산 데이터나 본학습에 편입하지 않는다.

## M24 — 독립 비행의 판정까지 실행 완료

이번에는 정상 조건의 새 랜덤 비행 3회를 각각 Gazebo GUI로 실행했다.
모두 180초 경로를 수행한 뒤 착륙/시동 해제로 완료됐으며 PX4/Gazebo 종료
코드는 각각 0이었다. 소유한 자식 프로세스의 종료도 확인했다.

| 용도 | seed | 기록 범위 | 분석 입력 | 연속 구간 |
| --- | --- | --- | --- | --- |
| 보정 1 | 20261121 | 229.48초 | 216.6초 | 1 |
| 보정 2 | 20261122 | 228.31초 | 215.9초 | 1 |
| 독립 평가 | 20261123 | 229.30초 | 216.9초 | 1 |

원본/적응 두 버전과 예측/종료 후 두 모델에 대해 총 4개 보정을 만들고
UI에서 활성화를 확인했다. 적응 모델도 두 개 모두 프로파일에 선택했다.
학습 1회·비교 1회·보정 2회·평가 1회의 수신 원본 SHA-256은 모두 달랐다.
최종 평가 전에 모델/선택/보정/계획 등 107개 파일의 해시를 잠갔으며 평가 후
모두 동일했다. 기준 초과를 줄이기 위한 사후 임계값 변경은 하지 않았다.

| 독립 평가 결과 | 원본 | CPU 적응 후 |
| --- | --- | --- |
| 예측 모델 전압 RMSE | 0.037709 V | 0.033517 V |
| 종료 후 모델 전압 RMSE | 0.276272 V | 0.267058 V |
| 예측 모델 판정 | 정상 범위, 0/206회 초과 | 정상 범위, 0/206회 초과 |
| 종료 후 모델 판정 | 정상 범위, 0/1구간 초과 | 정상 범위, 0/1구간 초과 |

예측 모델의 전압 오차는 약 11.1%, 종료 후 모델은 약 3.3% 감소했다.
예측 모델의 q/r 각속도 오차는 소폭 증가했다. 전압의 직전값 유지 RMSE는
0.014867 V로, 적응한 예측 모델도 이 단순 기준보다 여전히 나쁘다.
원본 역시 정상으로 판정했으므로 정상 판정 자체를 적응의 효과라고 해석하지 않는다.
이번 검증은 정상 비행 하나에서만 수행했다. 이상 탐지 능력이나 비행 단위
오경보율, 다른 경로·기체에 대한 일반화는 통과로 선언하지 않는다.

실시간 API를 약 1초마다 관측한 기록에는 정상 199회, 판정 불가 66회가 있다.
후자는 초기 연결/이력 준비와 착륙 후 송신 종료 및 분석 전환을 포함한다.
첫 예측부터 마지막 예측까지 206개 연속 관측은 모두 predicting이었으며,
그 구간의 상태 조회 최대 지연은 8.64 ms, 기록된 reset_count는 0이었다.
이 폴링 횟수는 독립 예측 횟수나 오경보율의 분모로 사용하지 않는다.
실제 저장 로그를 다시 점수화한 206개 예측 창에서 기준 초과는 0이었다.

종료 후 UI의 전체 런 요약은 94.6% 입력 사용, 정상 범위 1구간으로 표시됐다.
처음 9.6초는 필수 입력이 모이기 전, 마지막 약 2.8초는 climb_rate_error 입력이
없거나 오래된 구간이었다. 중간 구간을 임의 보간하지 않았으며 미분석 시간의
건강을 정상으로 확정하지 않았다. 화면 상단의 '실시간 판정 종료'와 하단의
비행 후 판정은 별개이며 실제 결과는 하단에 있다.

## 보존 확인과 남은 문제

- RC14 APP_MANIFEST의 19,854개 파일 모두 원래 해시와 동일하다. 기존 16종,
  scaler, 과거 보정과 제품 코드/배포 파일을 변경하지 않았다. 적응 모델은
  사용자 데이터 폴더에 새 버전으로 저장했다. 이전 두 비행의 근거 파일 10개도 동일했다.
- 제품 코드 변경이 없어 기존 전체 단위 시험을 반복하지 않았다. 대신 RC14
  자체에서 준비→CPU 학습→비교→등록→보정→실시간 판정→종료 후 분석을 실행하고,
  마지막 마일스톤에서 전체 배포 해시와 데이터 분리를 검산했다.
- **남은 성능 문제:** 여러 큰 저널이 쌓인 상태에서 종료 후 상태/목록 조회에
  약 9~11초가 걸린 요청이 있었다. 최종 평가의 최대 9.535초는 예측 구간 후였다.
  `StoreV2.list()`가 각 종료 세션을 `get()`으로 재생하고, `LocalLive.folder()`도
  존재 확인에 `get()`을 호출한다. 저널 캐시는 2개이므로 목록 조회 때 재파싱이
  반복될 수 있다. 이는 확인한 코드 경로이며 각 비용의 프로파일링은 추가로 필요하다.
  완료 manifest로 목록/존재 확인을 처리하는 개선은 아직 구현하지 않았다.
- **남은 표시 문제:** 종료 후 상단 실시간 영역의 '판정 불가' 문구가 하단
  '정상 범위' 결과와 혼동될 수 있다. '실시간 판정 종료'로 표시를 구분하는 개선 대기.
- RPM은 이 SITL에서 ESC 센서 메시지가 발행되지 않아 미수신이다. ESC 발행 확장과
  실물 FC/ESC 검증은 별도 대기다. PWM이나 시뮬레이터 정답을 RPM 관측으로 대입하지 않았다.
- 실제 BIN 3개는 건강 미확정으로 유지한다. 정상 근거가 있는 실기체 로그,
  실제 PX4 ULog/통신, 알려진 이상 사례가 확보되어야 실기체 적응/판정 성능을 검증할 수 있다.

세부 계획·요청·응답·분리 감사·검산 결과·화면은 로컬의
`ai/reports/adaptation-demo-20261115/`에 있다. 최종 검산은 `verification.json`,
전체 실제 BIN 화면은 `bin-all-summary.jpg`, 평가 판정 화면은
`eval-normal-verdict.jpg`다. 원시 로그와 모델은 Git에 올리지 않는다.
네 개발 지침은 `ai/reports/code-review-20261115/guidelines/`의 기존 조회본을 재확인했다.

## 같은 결과 열기

현재 PC에서 아래 명령으로 기존 데이터와 적응 모델을 다시 연다.
현재 실행 중이면 `start` 대신 `status`로 확인할 수 있다.

```bash
cd /home/sa/CapstoneV3
ARION_DATA_DIR="$PWD/ai/.local/rc13-ui" ARION_PORT=8879 \
  ./ai/releases/drone-local-ubuntu24-20261115-rc14/drone-local start
```

브라우저에서 `http://127.0.0.1:8879/`를 열고 비행 선택의
**X500 독립 평가 · 파인튜닝 및 판정**을 고르면 종료 후 결과를 볼 수 있다.
실제 BIN 전체 분석과 원본/적응 두 모델의 평가 결과는 **로컬 AI · 기체 관리**의
완료 작업에서 확인한다. 평가 작업은 원본 `5347226d`, 적응 `dbbc6c04`,
실제 BIN 전체 작업은 `38c9d755`로 시작한다.
새 데이터 폴더를 사용하면 이번 로컬 프로파일/적응/보정 등록이 없으므로
같은 결과가 자동으로 나타나지는 않는다.
