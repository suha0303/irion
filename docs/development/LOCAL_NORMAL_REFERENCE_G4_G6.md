# 정상 자료 활용과 판정 계산 일치 G4–G6

2026-11-15. 원본 가중치·scaler·과거 threshold·최종 평가 자료는 보존한다.
새 기체 보정은 `aircraft-final-protocol/1`로 구분하며 원격 GPU를 사용하지 않는다.

## 과거 100%의 범위

선택한 forecast Transformer h64/l4와 run_health Transformer h64/l2는
동결된 X500 평가에서 각각 이상 243/243, 배터리 급변 27/27을 검출했다.
정상 비행 오경보는 각각 38/486(7.82%), 15/486(3.09%)였다.
두 모델의 729개 저장 결과를 각각 다시 계산하여 모두 일치했고, 과거 정상/이상
각 1회의 CPU 재추론도 기존 판정을 재현했다. 따라서 당시 100%는 그 시험의
이상 비행 재현율이며, 모든 입력의 정확도나 현재 실기체 성능이 아니다.

현재 UI의 기존 경로는 같은 원본 가중치를 사용하면서 forecast의 마지막 1초
시점 최대 표준화 절대오차와 단일 경험적 기준으로 판정했다. 과거 평가의
10개 예측 시점·추진/배터리 별 점수·시간 후처리와 달랐다. 종료 후 점수도
short/long 잔차의 개별 정상 척도를 사용하지 않았다. 이전 보고에서 이를
설명하지 않고 단순히 ‘원본도 미탐’이라고 한 것은 불충분했다.

과거 계산과 임계값을 현재 정상 3회·배터리 이상 1회에 그대로 적용하면 4회
모두 경보였다. 이상 비행의 첫 배터리 경보는 실제 고장 약 51초 전이었다.
가중치 손상으로 확인된 것이 아니며, 기준값까지 무조건 복사해서 검출 개선으로
보고할 수 없다. 실제 입력 분포 차이는 확인했지만 기동·수신·운용 조건의
개별 인과 기여는 분리하지 않았다. 배터리 파라미터 내용은 과거와 같았고
기존 native 전처리의 profile ID 불일치는 우회하지 않았다.

증거: `ai/reports/final-vs-local-20261115/audit.json`, `input-distribution.json`.

## 구현

- `localflight.detector`가 동결 평가의 점수·경보 코드를 호출한다. Forecast는
  전체 10개 lead의 제곱 잔차를 정상 개발 자료의 lead/target별 q95 척도로 나눈다.
  추진 3개 target 평균과 배터리 전압 평균을 분리하고, 기존 EWMA·3회 진입·10회
  해제 조건을 적용한다. 기존 평가 코드를 복사하거나 수정하지 않았다.
- Run health는 기존 short/long 계산과 각각의 정상 척도, 최대 표준화 성분을
  사용한다. 보정 비행이 적어 95% 유한 표본 순위가 없으면 정상 보정 점수의
  최대를 **잠정 경험적 기준**으로 사용한다. 이를 5% 오경보율 보장으로 표시하지 않는다.
- 정상 개발 자료와 정상 임계값 보정 자료를 분리한다. 학습/개발/보정 자료를
  독립 평가 비행에 재사용하지 않는다. 판정 정책이 다른 예전 보정 파일은 보존하고,
  명시적 버전 선택 때 같은 기체·모델·입력의 판정 정책도 함께 전환한다.
- `CausalSampler`를 로그 분석과 실시간 분석이 공유한다. 실시간 청크 사이에
  필터 상태를 유지하고 같은 연속 구간의 1초 간격 forecast origin을 사용한다.
  미래 실측 10개가 도착해야 판정한다. 구간 중단/재부팅 경계를 넘지 않는다.
- UI 이상 목록은 단순 점수 비교를 다시 하지 않고 실제 후처리 경보 플래그를
  표시한다. 고장 전부터 유지된 경보는 새 고장 검출 성공으로 세지 않는다.
  종료 후 전압 모델에는 추진계 고장 검출을 요구하거나 성공으로 주장하지 않는다.
- 정상 비행 자동 배치는 입력 분포(q01/q50/q99), 보존 시간, 역할별 자료를
  남긴다. 원본 SHA로 정렬하여 점수를 보기 전에 배치하고 원본은 변경하지 않는다.
  개발 비행 여러 회의 학습 중 비교는 비행별 동일 가중 평균을 사용한다.
- 상세 비교가 커져도 모델 선택 요청은 저장 파일과 SHA만 전달한다. 64 KiB
  요청 한도를 늘리거나 상세 증거를 버리지 않는다.
- 보정 패널은 파인튜닝 패널 아래 같은 열에 배치한다. 두 모델 작업과 별도
  수동 보정의 용도를 설명하고, 수동 보정도 정상 기준용 개발 비행을 받는다.

## 데이터 수의 권장 시작점

| 정상 비행 | 가능한 범위 |
|---|---|
| 1–3회 | 입력·시간축 확인, 초기 적응/정상 오차 참고. 독립 검증 자료 부족 |
| 5회 | 학습 1·개발 1·보정 2·정상 평가 1로 최소 역할 분리 |
| 10–20회 | 다양한 기동·잔량·하중·온도 조건으로 정상 범위와 오경보 비교 |
| 20회 예시 | 학습 3·개발/정상 척도 3·보정 8·정상 평가 6 |

10–20회는 공학적 권장 시작점이며 연구에서 보장된 최소 표본 수가 아니다.
서로 다른 파일 수가 아닌 실제 독립 비행 수로 센다. 20회 전체를 학습에 넣지 않는다.
알려진 이상 로그는 학습·기준 생성에 사용하지 않고 검출·퇴행 시험에 별도로 쓴다.
정상 여부가 불명확한 실기체 BIN 3개는 정상 학습에 사용하지 않는다.

## 새 PX4 20회 시험

사용자가 정상 약 20회의 병렬 수집과 전체 시험을 명시 승인했다.
시험 계획은 `ai/reports/normal20-20261115/attempt-02/plan.json`에 수집 전 고정했다.
4개 독립 PX4 instance·UDP 포트·Gazebo partition, 1배속, 회당 mission 180초다.
서로 다른 seed의 랜덤 경로와 SOC 0.72–0.95, 온도 288.15–303.15 K,
추가 하중 0–0.08 kg, 작은 고정 바람 조건을 사용한다.
정상 20회 외에 배터리 step/ramp·추진계 step/ramp 4회를 평가한다.

초기 기록기의 `bytearray` 직렬화 실패 4회는 별도 증거로 남겼다. 이번에 직접
시작한 비행만 종료하고 기록기를 수정했으며, 같은 seed/조건으로 재수집했다.
원시 native 데이터와 수신 로그는 삭제하지 않는다. 물리 고장 시각은 실제
ATTITUDE의 boot/receipt 시각 쌍으로 평가용으로만 대응한다.
신경망 입력의 수신 시계나 실측값을 고장 정답에 맞춰 보정하지 않는다.

수집은 24/24회 완료했다. 모두 PX4/Gazebo와 기록기 종료 코드 0이며, 정상 20회는
기존 정상 선택·운용 범위 검사를 통과했다. 각 로그의 사용률은 93.22–93.81%,
합계 51,870시점/5,187초다. 초기 필수 입력 미수신 약 14–15초는 제외했다.

수집 전에 정한 학습 3·개발 3·보정 8·정상 평가 6·이상 평가 4를 유지했다.
별도로 정상 20회의 자동 배치 기능도 검증했으나 SHA 정렬 배치와 이번 고정 역할을
섞지 않았다. 최상의 과거 평가 모델 두 종만 각 30 epoch 부분 학습했다.
원본과 후보에 같은 정상 자료·점수·후처리·기준 생성 절차를 적용했다.

|---|---:|---:|
| Forecast 정상 오경보 | 0/6회 | 0/6회 |
| Forecast 고장 이후 해당 영역의 새 경보 | 0/4건 | 0/4건 |

RTX 4060 Laptop에서 선택한 두 모델의 학습·보정·비교·별도 CPU 2.1.2 복원은
24.643초였다. 학습 자체는 각각 12.843초/1.203초다. 환경 설치·24회 수집·원시
준비·추가 진단 시간은 제외하며 RTX 3050 실측으로 환산하지 않는다.
Forecast는 알려진 이상 미탐과 일부 정상 신호 오차 증가로, run health는 배터리
미탐으로 **적용 거절**했다. 평균 전압 오차 개선을 검출 성능 개선이라고 하지 않는다.
후보와 증거는 보존하고 활성 모델을 자동 교체하지 않았다.

### 미탐 원인 추적

- 4회 모두 실제 native truth의 fault_applied와 목표 파라미터 도달을 확인했다.
  배터리는 용량 12.357→10.189 Ah, R0 0.02051→0.02818 Ω로 변했다.
  추진계는 모터 저항 0.115→0.1196 Ω, 추력계수 약 1% 감소 등 기존 고장을 적용했다.
- 정상 보정 비행의 큰 점수는 주로 최초 예측 부근(수신 기준 약 21–23초)에 있었다.
  원본 forecast의 정상 보정 기준은 추진 87.44, 배터리 5.98이었다. 고장 후 해당
  영역 최대 EWMA/기준 비율은 배터리 step/ramp 0.202/0.153,
  추진 step/ramp 0.036/0.127이었다. 초반 과도 오차를 포함한 전역 기준이 작은
  고장 잔차를 가린 것은 확인했다. 그 과도 오차의 입력별 원인은 아직 분리하지 않았다.
- 정상 비행 하나의 큰 종료 후 전압 오차가 run health의 경험적 최대 기준을 결정했다.
  두 배터리 이상 점수는 원본 기준의 0.521/0.421배였다.
- 추진 step 비행은 원본/후보 모두 전체 런에 경보가 있다. Forecast 경보가 고장
  전에 발생했고, 종료 후 전압 경보를 추진 고장 검출로 세지 않으므로 위 표의
  유효 검출은 0건이다. 단순히 ‘이상 파일에 경보가 하나 있음’으로 성공 처리하지 않는다.
- 따라서 점수 계산 통일만으로 현재 운용 조건의 검출 문제가 해결되지는 않았다.
  이상 정답을 보고 기준을 낮추거나 초기 구간을 임의 삭제하지 않았다.

### 실시간·저장 결과 일치

새 평가 비행 10회 × 원본/후보, 합계 4,114개 예측 블록에서 실제 타깃 10개의
도착 처리와 파일 분석을 비교했다. 최초에는 JSON float64/실시간 float32 제곱의
반올림 차이(최대 약 1.70e-9)로 완전 일치 검사가 실패했다. 점수 계산의 잔차를
명시적으로 float64로 통일한 뒤 **점수와 경보 모두 정확히 일치**했다.
모델을 재학습하거나 정상 기준을 재생성하지 않았으며 첫 실패 로그도 보존했다.
평가 전 봉인의 코드 중 `localflight/detector.py`만 이 정밀도 수정으로 바뀌었다.
원본 모델/scaler 봉인은 모두 일치한다. 이는 도착 처리 재생 시험이며 24개 비행에서
UI의 실시간 추론 이력까지 새로 생성했다는 뜻은 아니다.

실행 증거: `ai/reports/normal20-20261115/summary.json`, `miss-diagnosis.json`,
`flight23-preexisting-alarm.json`, `pre-evaluation-seal.json`, `evaluation-01/`.

### 다음 성능 마일스톤

1. 정상 개발 자료만으로 초기 이력·이륙/기동·착륙의 오차와 입력 수신 상태를 분리한다.
   실제 로그에서도 관측할 수 있는 상태만 사용하고 판정 제외 범위는 명시한다.
2. 운용 상태별 정상 기준, 더 긴 전압 변화/잔차 누적, 정상 기반 보조 탐지기를 비교한다.
   기존 예측기를 더 오래 학습하는 것만으로 검출이 개선된다고 가정하지 않는다.
3. 이번 20+4회는 이제 개발/회귀 자료로 고정한다. 방법을 선택한 뒤 새 seed·새 조건의
   정상/이상 최종 평가를 별도로 봉인한다. 실기체 검증과는 계속 구분한다.
